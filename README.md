# Chess

A fully playable two-player chess game built in Python using pygame. This started as a personal project to see how far I could take a well-defined game, complicated enough to be interesting, but grounded enough that I wouldn't get lost.

---

## Current State

The game is complete and playable. Two players can sit down and play a full game of chess with all standard rules enforced. It's missing threefold repetition, but everything else is in.


## Features

- All standard piece movement
- Legal move generation via board simulation
- Check, checkmate, and stalemate detection
- Castling (kingside and queenside)
- En passant
- Pawn promotion with piece selection UI
- Fifty-move rule
- Insufficient material detection
- Move history
- Visual highlights for selected pieces, legal moves, and check


## Tech Stack

- **Python**
- **pygame** — rendering and input
- **dataclasses** — move and history representation

I already knew Python from previous projects, including a checkers game that served as a pygame warmup. Before that, my first complete game was a snake game in C using SDL2, so pygame felt like a natural step up.

## Architecture



### GameState and GameUI — Separated by Design

The biggest architectural decision was keeping `GameState` and `GameUI` completely decoupled. Neither holds a reference to the other. They communicate exclusively through **actions** and **commands**:

- **Actions** flow from `GameUI` → `GameState` (user input translated into intent)
- **Commands** flow from `GameState` → `GameUI` (what changed, what to render)

This was loosely inspired by REST and client/server architecture — the idea that two systems can stay independent as long as they agree on a contract for communication. It made the codebase harder to follow in places but much easier to reason about in isolation.

### State Machine

The game loop is driven by a state machine with the following states:

```
GAME_START → START_TURN → SELECT_PIECE → SELECT_MOVE → END_TURN → START_TURN → ...
                                                    ↘ SELECT_PROMOTION ↗
```

Each state has:
- A **handler** — validates input and decides what happens next
- **on_exit** — cleans up the current state (clears highlights, resets attributes)
- **on_enter** — sets up the new state (builds move dict, issues UI commands)

`on_enter` and `on_exit` are the least obvious parts of the codebase. They don't make decisions, by the time they run, the handler has already decided where the game is going. They just handle the transition mechanics.

### Move Representation

Moves started as plain tuples `(row, col)`. As special moves like castling and en passant were added, this became unworkable. Moves are now objects:

```python
Move(from_square, to_square, kind=MOVE_NORMAL, payload=None)
```

The `kind` field is one of `NORMAL`, `CAPTURE`, `EN_PASSANT`, or `CASTLE`. The `payload` carries any extra data the move needs — for castling, the rook's from and to squares; for en passant, the captured pawn's square.

This let `apply_move` on the board handle all move types in one place by switching on `kind`, rather than scattering special-case logic across the codebase.

### Legal Move Generation

Move generation works in two phases:

1. **Pseudo-legal moves** — generated by each piece, valid in isolation (correct movement pattern, not blocked by allies)
2. **Legal moves** — filtered by simulating each pseudo-legal move on a ghost board and checking whether the king ends up in check

The ghost board is a lightweight copy of the real board. I wanted to perhaps remove this but that change was out of scope.

### Move History

Completed moves are stored as `HistoryEntry` objects — immutable snapshots containing the piece kind, color, from/to squares, and optional data for captures, promotions, and castling. This is separate from the `Move` class, which is a live instruction. The distinction is: a `Move` describes what should happen; a `HistoryEntry` records what did.



## Constraints & Scope Decisions

A few omissions in this project were deliberate rather than accidental.

**No AI opponent.** 
- I looked into Minimax and it's implementable, but game AI isn't something I'm particularly interested in and it felt outside the scope of what I was trying to build. The foundation is there if I wanted to build it later, I might. 

**No networking or multiplayer.** 
- I have no idea how to set up networking, and I wasn't going to learn it for this project. Almost everything in this codebase was figured out myself. I deliberately limited outside knowledge because I wanted to learn programming, not networking.

**Why pygame.** 
- I used SDL2 in C for my first game and heard pygame was similar. It was. Familiar enough to be productive, different enough to still be interesting.

**Ghost board simulation over move undo.** 
- Simulating moves on a ghost board was easier to implement and fit naturally with how moves were represented at the time — pieces mapping to destination tuples. A move undo approach would have required a more complete reversal system from the start, which wasn't worth the upfront investment.

**No bitboards.** 
- I wasn't aware of them during development. Having looked at them since, they're an interesting optimization — representing the board as 64-bit integers for fast move generation. For a human-speed two-player game the performance difference doesn't matter, but still pretty cool.

**No animations, music, or menus.** 
-  I built a main menu and reset system for a previous game. Once you've done it once it stops being interesting. I wanted to focus on the chess logic, not the flourishes.


## Evolution of the System

The earliest version was close to checkers, just pawns, basic movement, nothing special. Over time:

- **Tuple moves → Move objects** — special moves forced a richer representation
- **Direct UI mutations → command/action pipeline** — UI and game logic were originally tangled; separating them was the most impactful refactor
- **Implicit special-case detection → explicit move kinds** — castling was initially detected by checking if the king moved two squares; encoding it in the move itself was cleaner and more honest

A lot of time went into refactoring rather than building features. In hindsight, a MoSCoW-style feature list at the start would have helped me stop refactoring and start shipping.


## Interesting Problems

**Fitting castling and en passant into a uniform move system** was the hardest design challenge. Both involve multiple pieces or non-obvious capture squares that don't fit the standard "move to destination" model. The solution — encoding the extra data in the move payload — took a few iterations to land on.

**Ghost board state** was the weirdest bug. Pieces were behaving strangely during legal move generation because the ghost board wasn't being fully isolated from the real board. The fix was making sure `double_jumped_pawn` and other transient state were properly copied into the ghost.

**The circular import between `Piece` and `GameBoard`** — pieces need to know about the board to generate moves, and the board holds pieces. Resolved with `TYPE_CHECKING` and quoted type hints.


## What I Learned

Chess rules are mostly edge cases. The basic movement is straightforward, the complexity is entirely in the exceptions.

Even a simple game has a lot of moving parts. Just getting a piece to render on screen, respond to a click, and move correctly involves more steps than it looks like from the outside. Python is a high-level language. I can only imagine doing this in C.

Small design decisions compound. Naming, ownership, where logic lives, these feel like minor choices early on and become load-bearing walls later.

Working alone on a well-defined project is very different from working in a team on something evolving. I had maybe three or four merge conflicts over the whole project, all from forgetting to update main. In my 401 course project we had conflicts constantly. Scale changes everything.


## Things I'd Do Differently

**Plan features upfront.** I spent a lot of time refactoring systems that were already working well enough. A simple checklist of must-have features would have kept me focused on building rather than improving.

**Write board-state tests earlier.** The project changed shape too quickly in the early stages for strict TDD to be practical. But once the architecture stabilized, targeted tests around move legality and edge cases would have caught several bugs faster.


## Future Improvements

Roughly ordered by assumed difficulty:

- **AI opponent** — would require significant refactoring and a search algorithm
- **Undo / redo** — the `HistoryEntry` structure is mostly ready; needs reversal logic, commands and a robust game state redefinition
- **Timers** — unclear difficulty; likely needs a UI component
- **Game loading** — consume a pre-set board from an external source (PGN or similar)
- **Threefold repetition** — board state hashing, probably the easiest of these


## AI Usage

The notes and documentation throughout this project were written by me. This README was written from my own notes with AI used as a writing companion to help structure and rewrite them, similar to how you might use an editor.

For the code itself, I deliberately avoided using AI to generate solutions. I wanted to learn. AI was used more like a rubber duck, something to think out loud with, that would nudge me in the right direction without handing me the answer. The features I'm most proud of, the state machine and the action/command system, are things I designed myself.

Where AI genuinely helped: naming variables, methods, and classes; writing commit messages; and the occasional syntax question when my brain was tired. Around 90% of the code is mine. If it's English prose or a comment, it was probably written by me and cleaned up with AI assistance.

I also intentionally kept LLM context small and didn't use any agentic tools like Claude Code.


## Personal Reflection

The most satisfying moment was getting castling and en passant working correctly within the action/command system. Both moves had resisted fitting neatly into the existing architecture for a while, when they finally clicked, it felt like the system actually worked the way it was supposed to.

The most frustrating part was the UI. Always the UI. It's repetitive, with just enough variation between components to prevent proper automation. It works, but it wasn't fun to build.

The part I'm most proud of is the separation between `GameState` and `GameUI`. It was hard to get right and easy to break, but the end result is two systems that genuinely don't know each other exist. 

If you're reading the code please pay attention to `on_enter_state` and `on_exit_state`. They're the least obvious part of the system and do more than they look like they do.
